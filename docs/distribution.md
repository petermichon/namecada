# Distribution

The Android build ships two ways without a store: tagged GitHub releases that
[Obtainium](https://obtainium.imranr.dev) follows, and OSS repositories
(IzzyOnDroid now, F-Droid when its build server can take the recipe). Nothing
here is Play-specific; the on-device engine means there is no server to operate.

## Versioning and versionCode

`tauri.android.versionCode` is derived from `version` in
`apps/desktop/src-tauri/tauri.conf.json` as `major * 1000000 + minor * 1000 + patch`, so
`0.1.0` becomes `1000`. Every release needs a higher `version` and therefore a
higher `versionCode`; Android refuses a downgrade and Obtainium will not offer
one. The release workflow fails if the pushed tag does not match the version.

Tag releases as `v<version>` (`v0.1.0`), never a bare build number.

## Signing key

The same key must sign every release forever. Regenerating it means every user
has to uninstall and lose their cached verdicts and recent labels. Keep the
keystore outside the repository (see `docs/android.md`) and back it up.

```sh
base64 -w0 ~/.config/namecada/release.jks   # NAMECADA_KEYSTORE_B64
```

Repository secrets for `.github/workflows/android.yml`:

| Secret | Value |
| --- | --- |
| `NAMECADA_KEYSTORE_B64` | the base64 above |
| `NAMECADA_KEYSTORE_PASS` | store password |
| `NAMECADA_KEY_PASS` | key password |

## GitHub releases → Obtainium

`.github/workflows/android.yml` runs on a `v*` tag, builds the frontend, runs
`tauri android init` (the generated project is gitignored), builds a universal
APK plus one APK per ABI, signs each with the keystore, and attaches them to the
release with SHA-256 sums.

Obtainium then needs nothing from us: point it at
`https://github.com/petermichon/namecada` and it reads the release assets on
every check. The universal APK is the safe default; the per-ABI files exist
because a store may cap the download size — a universal build is about 47 MB,
arm64 alone about 12 MB.

## Repository metadata (Fastlane)

F-Droid and IzzyOnDroid both read `fastlane/metadata/android/en-US/` from the
repository, so the listing lives next to the code:

- `short_description.txt` — at most 80 characters
- `full_description.txt`
- `images/icon.png` — 512×512
- `images/phoneScreenshots/` — at least two portrait screenshots

Screenshots must show the app on a phone. Grab them from the device rather than
reusing the desktop captures in `docs/`:

```sh
adb exec-out screencap -p > fastlane/metadata/android/en-US/images/phoneScreenshots/1-home.png
```

## IzzyOnDroid

File an inclusion request in [their tracker](https://codeberg.org/IzzyOnDroid/repodata/issues)
with the repository URL, the license (MIT OR Apache-2.0), the category
(Internet), and the release that carries the APK. They test the APK on a device,
scan it, and check the Fastlane metadata.

Two of their rules matter here:

- the APK must be signed with the release key, not a debug key, and must not be
  `debuggable` or `testOnly` (the release build type already clears both);
- they reject apps whose code was generated by AI assistants. That is a policy
  judgement about this project's history, not a technical failing; decide
  before filing whether it applies and disclose it rather than have it found.

## F-Droid

F-Droid builds from source on its own server and signs with its own key, so its
APK cannot replace an Obtainium one — switching means uninstalling.

The build recipe lives in `fdroiddata` as
`metadata/com.namecada.app.yml`. A starting point, based on other Tauri apps in
the repository:

```yaml
Categories:
  - Internet
# F-Droid wants one SPDX identifier; the code is dual MIT OR Apache-2.0, so the
# recipe names the permissive half a recipient would pick anyway.
License: MIT
SourceCode: https://github.com/petermichon/namecada
IssueTracker: https://github.com/petermichon/namecada/issues
RepoType: git
Repo: https://github.com/petermichon/namecada

Builds:
  - versionName: 0.1.0
    versionCode: 1000
    commit: v0.1.0
    timeout: 14400
    sudo:
      - apt-get update
      - curl -fsSL https://deb.nodesource.com/setup_22.x | bash -
      - apt-get install -y nodejs
    srclibs:
      - rustup@1.27.1
    prebuild:
      - $$rustup$$/rustup-init.sh -y --default-toolchain stable
      - . "$HOME/.cargo/env"
      - rustup target add aarch64-linux-android armv7-linux-androideabi i686-linux-android x86_64-linux-android
      - cargo install cargo-ndk tauri-cli --locked
      - npm ci
      - npm run build
      - export ANDROID_HOME=$$SDK$$ NDK_HOME=$$NDK$$
      - (cd apps/desktop && npx tauri android init --ci)
      - (cd apps/desktop && npx tauri icon src-tauri/icons/app-icon-manifest.json)
    build:
      - export ANDROID_HOME=$$SDK$$ NDK_HOME=$$NDK$$
      - npm run build
      - (cd apps/desktop && npx tauri android build --apk)
    output: apps/desktop/src-tauri/gen/android/app/build/outputs/apk/universal/release/app-universal-release-unsigned.apk
    ndk: 27.0.12077973
```

Points that need checking against `fdroiddata` before filing:

- **NDK pin.** The template generates `compileSdk`/`targetSdk` 37 and wants the
  NDK the toolchain names (`30.0.16248370` in `docs/android.md`); the recipe can
  only use an NDK the build server publishes, so the generated project may need
  to be pinned down to that version.
- **JDK.** AGP 9.3 needs a full JDK with `javac`; confirm the server's version.
- **Anti-feature.** F-Droid will want `AntiFeatures: NonFreeNet`, because the
  app queries third-party services.
- **Reproducible builds** are optional but recommended, and expensive for Rust
  targets: they need a fixed `CARGO_HOME`, `CARGO_TARGET_DIR`, matching
  `--remap-path-prefix` and identical toolchains.

Until that lands, `fdroiddata` review is a conversation, not a checklist.
